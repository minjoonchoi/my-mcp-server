# 권한 톡 v2 — 조회와 관계 관리

MCP 서버가 준비되면 **http://127.0.0.1:8080/chat.html** 에서 엽니다. 같은 출처의 고정 `/mcp`를 호출하는 순수 HTML/CSS/JavaScript UI입니다. 별도 FE 서버·CORS·프레임워크·외부 CDN·LLM은 사용하지 않습니다. 정해진 한국어 읽기 질문과 명시적인 관리 양식을 제공합니다. “무엇을 할 수 있나요?” 안내에서 도구 이름이나 ID를 외우지 않고 실제 조회를 시작할 수 있습니다.

## 연결과 조회

1. 이번 서버에서 검증할 **개발용 MCP 클라이언트 토큰**을 password 입력란에 붙여 넣고 **연결하기**를 누릅니다. `Bearer ` 접두사는 제외합니다. API용 위임 토큰·서비스 자격 증명·개인키를 브라우저에 넣지 않습니다.
2. 실제 MCP 초기화, 초기화 알림, 도구 12개의 스키마·어노테이션 확인이 끝나면 **연결됨**으로 표시합니다.
3. 목적별 안내의 버튼이나 예시 질문을 클릭하거나 아래 읽기 질문을 입력합니다. 반환된 범위만 표시하며 데이터나 접근 경로를 만들어 내지 않습니다.
4. **최신 상태 조회**는 현재 사용자 권한, 카탈로그 4종, 요청 가능한 역할을 새로 읽습니다. 변경 도구를 호출하지 않습니다.
5. 종료하거나 계정을 바꿀 때 **연결 해제**를 누릅니다. 토큰·이전 결과·대상 ID·진행 중 미리보기를 지웁니다.

## 목적별로 시작하기

연결 전에도 아래 5가지 안내·예시·입력 조건이 보입니다. 연결하지 않고 버튼을 누르면 네트워크 요청 없이 연결 안내를 표시하고 토큰 입력으로 포커스를 옮깁니다. 연결 후 버튼은 기존 실제 MCP 읽기를 수행합니다.

| 목적 | 시작 방법 | 입력과 권한 |
| --- | --- | --- |
| 내 권한과 리소스 | **내 권한 관계 보기** → 내 사용자·역할·정책·리소스 요약과 부여 경로 | 추가 입력 없음, 조회 권한 필요 |
| 항목 찾아보기 | 종류 선택 → **목록 불러오기** → 실제 항목 선택 또는 정확한 ID → **상세 보기** | 사용자/역할/정책/리소스 중 선택, 조회 권한·서버 공개 범위 적용 |
| 요청 가능한 역할 | **요청 가능 역할 보기** → 공개 이름과 설명 | 추가 입력 없음, 조회 권한 필요, 신청 제출·승인 기능 없음 |
| 관계 관리 | **관리 양식 열기** → 작업 선택 → **허용된 대상 목록 불러오기** → 대상 선택 → 미리보기 | 정확한 대상 2개, UI는 조회+변경 권한·DB 관리자 필요 |
| 권한 개념 이해 | **개념 설명 보기** → 역할과 정책의 차이 | 추가 입력 없음, 조회 권한 필요, 실제 부여 권한과 별개 |

관계 보기의 요약과 경로는 검증된 실제 `get_my_access` 응답만으로 구성합니다. 각 경로는 사용자 → 역할 → 정책 → 리소스의 이름·ID를 함께 표시하며 서로 다른 부여 경로를 모두 유지합니다. 리소스까지 이어지는 경로가 없으면 빈 상태를 표시하고, 역할·정책 수를 별도로 안내합니다. 결과 갱신이 실패하면 이전 그래프를 새 결과인 것처럼 보여주지 않습니다.

목록 선택지는 현재 연결에서 실제 허용된 응답의 ID로만 만듭니다. 상세 조회는 다시 `get_access_entity`를 호출합니다. 이름이나 선택지의 공개 여부가 관리 권한을 부여하지 않습니다. 관리 목록의 보호된 항목은 **보호됨, 선택 불가**로 표시하고 선택을 차단합니다. 목록이 비거나 읽기가 거부되면 이유를 안내하며 정확한 ID 직접 입력은 유지하되, 기존 미리보기와 서버 인가 검증을 반드시 거칩니다.

작업 중 안내 버튼·중복 요청은 잠기며 로딩 상태를 표시합니다. 목록·관계·신청 가능 결과의 빈 상태, 잘못된 응답, 권한 거부를 각각 안내합니다. 모든 입력과 선택기에 label을 연결하고 기본 버튼·select·details의 키보드 동작을 사용합니다. 연결 안내는 토큰 입력, 관계 조회는 결과 제목, 상세 조회는 결과 영역, 목록 선택은 상세 버튼, 관리 준비는 작업 선택으로 포커스를 이동합니다. 작은 화면에서는 카드를 한 열로 배치하고 도구 영역의 높이 제한을 해제합니다. 실제 브라우저의 화면·키보드·모바일 검증은 TESTER가 수행합니다.

| 입력 예시 | 호출 도구와 인수 | 의미 |
| --- | --- | --- |
| 내 정보 알려줘 / 내 역할은 뭐야? / 나에게 적용된 정책은? / 접근 가능한 리소스 알려줘 / 내 권한 관계 보여줘 | `get_my_access({})` | 자신의 프로필과 전체 역할 → 정책 → 리소스 경로 |
| 리소스 R100에 접근할 수 있어? 왜? | `check_my_resource_access({resourceId:"R100"})` | 현재 사용자의 접근 여부와 실제 부여 경로 |
| 역할과 정책은 어떻게 달라? | `explain_authorization({concept:"overview"})` | 정적 개념 설명. 실제 권한 근거와 구분 |
| 사용자 목록 / 역할 목록 / 정책 목록 / 리소스 목록 | `list_access_entities({entity:"users"})` 등 | 서버가 허용한 카탈로그 목록 |
| 사용자 U100 상세 / 역할 reader 상세 / 정책 read 상세 / 리소스 R100 상세 | `get_access_entity({entity:"users",id:"U100"})` 등 | 정확한 ID의 상세. 예시 ID는 실제 목록에서 확인한 ID로 바꿉니다. |
| 요청 가능한 역할 알려줘 | `get_requestable_roles({})` | 직접 보유하지 않은 요청 가능·비보호 역할의 공개 메타데이터 |

`권한이 뭐야?`, `역할이 뭐야?`, `정책이 뭐야?`, `리소스가 뭐야?`는 각각 `permission`, `role`, `policy`, `resource` 개념을 요청합니다. 일반 사용자의 카탈로그 범위는 본인과 본인의 권한 그래프이며 DB 관리자는 전체 카탈로그를 볼 수 있습니다. **UI가 표시 범위나 관리자 여부를 자체 결정하지 않습니다.** 보이지 않는 상세와 없는 상세는 동일한 `NOT_FOUND` 안내를 사용합니다.

요청 가능한 역할은 실제 부여 권한이 아니며 신청·승인 기능도 아닙니다. 다른 역할을 통해 같은 유효 리소스 권한을 갖더라도 해당 역할을 직접 보유한 것으로 취급하지 않습니다. 이 공개 역할 목록은 그 역할의 정책·리소스를 열람할 권한을 주지 않습니다.

리소스 접근 질문은 `R` + 숫자 3자리 ID를 사용하며 소문자 `r100`도 정규화합니다. 이름으로 질문하면(예: `리소스 운영 대시보드에 접근할 수 있어?`) 현재 토큰으로 새 `get_my_access`를 호출해 **정확하고 유일한 접근 가능 이름**만 ID로 해석합니다. `Report.A`와 `ReportA`를 구분하며 이름 내부 문장부호를 보존합니다. 모호하거나 일치하지 않는 이름은 ID 입력을 안내하고 접근 확인 도구를 호출하지 않습니다.

## 관계 관리: 미리보기 → 실행

1. **관리 양식 열기** 후 **작업**을 선택하고 **허용된 대상 목록 불러오기**로 두 종류의 실제 카탈로그를 읽어 대상을 고르거나, 조회 결과에서 확인한 대상 ID 두 개를 정확히 입력합니다. 관리 양식은 ID 대소문자나 공백을 자동 교정하지 않습니다.
2. **변경 미리보기**를 누릅니다. 이 단계는 `get_my_access({})`로 현재 실행자를 확인할 뿐 변경 요청을 보내지 않습니다. 실행자는 서버가 검증한 토큰의 사용자이며 대상 `userId`와 다릅니다. 로컬 사용자 ID가 JWT subject와 같다고 가정하지 않습니다.
3. 현재 실행자, 추가/해제할 관계와 대상 ID를 확인합니다. **변경 실행** 버튼을 명시적으로 클릭할 때만 고정된 미리보기의 operation·인수·실행자·연결 세대 스냅샷을 사용해 요청합니다. `approved` 같은 인수는 보내지 않습니다.
4. 실행 전 **취소**하거나 작업·대상·계정을 변경하면 미리보기를 버립니다. 폼 제출/Enter는 미리보기만 생성하며 읽기 질문·자연어 관리 요청·재연결은 변경을 실행하지 않습니다. 실행 버튼의 의도적인 키보드 활성화는 클릭과 동일합니다.
5. 결과의 `changed`, 처리 시점 `present`, 영향 가능 사용자 ID를 확인합니다. 완료 후 현재 사용자 권한과 모든 카탈로그·요청 가능 역할을 다시 조회합니다. 조회가 거부되거나 실패하면 확인하지 못했음을 표시합니다.

| 작업 선택값 / MCP Tool | 정확한 대상 인수 | 처리 시점 관계 |
| --- | --- | --- |
| `assign_role_to_user` | `userId`, `roleId` | 존재 |
| `remove_role_from_user` | `userId`, `roleId` | 없음 |
| `attach_policy_to_role` | `roleId`, `policyId` | 존재 |
| `detach_policy_from_role` | `roleId`, `policyId` | 없음 |
| `attach_resource_to_policy` | `policyId`, `resourceId` | 존재 |
| `detach_resource_from_policy` | `policyId`, `resourceId` | 없음 |

사용자·역할·정책 ID는 `^[A-Za-z0-9_-]{1,64}$`, 리소스 ID는 `^R[0-9]{3}$`입니다. 예를 들어 실제 목록에서 확인한 사용자 `U200`에 역할 `reader`를 추가한다면 작업 `assign_role_to_user`, 첫 대상 `U200`, 두 번째 대상 `reader`를 입력하고 미리보기 후 실행합니다. 이는 예시이며 해당 ID의 존재나 변경 권한을 보증하지 않습니다.

관리 권한은 서버에서 매번 검증합니다. **조회는 `authz.read`, 변경은 `authz.manage`와 현재 DB의 보호된 관리자 역할 멤버십이 필요**합니다. 관리자는 읽기 전용 토큰만으로 변경할 수 없고, 일반 사용자는 manage scope가 있어도 변경할 수 없습니다. 보호된 역할·정책·리소스를 끝점으로 하는 관계는 관리자도 변경할 수 없습니다. UI 미리보기나 Tool annotations는 서버 검증을 대신하지 않습니다.

이 UI는 실행자를 검증하기 위해 읽기 미리보기를 요구하므로 **관리 흐름에 read+manage가 필요**합니다. API/MCP 자체는 DB 관리자+manage-only 토큰의 변경을 허용하지만, UI에서는 read가 없어 실행자 미리보기를 만들 수 없다고 안내합니다. 미검증 JWT decode로 실행자를 추정하지 않습니다. TESTER는 manage-only 조합을 직접 HTTP/MCP에서 별도로 검증합니다.

`changed:false`는 중복 추가/이미 없는 링크 해제 같은 정상적인 변경 없음입니다. `present`는 해당 트랜잭션 처리 시점의 상태이며 후속 변경이 없다는 보장은 아닙니다. 영향 가능 사용자 목록은 모든 사용자의 유효 권한이 반드시 늘거나 줄었다는 뜻이 아닙니다. 다른 역할·정책 경로가 있으면 해당 접근은 유지될 수 있습니다.

## 전송 후 취소와 결과 미확인

**이미 전송한 변경의 취소는 롤백이 아닙니다.** 취소·12초 제한·연결 유실·잘못되거나 128 KiB를 초과한 응답으로 성공 응답을 받지 못해도 서버가 변경을 완료했을 수 있습니다. UI는 이를 **결과 미확인**으로 표시하고 실패·롤백을 확정하지 않습니다. 변경 요청을 자동 재시도하지 않습니다.

동일 연결의 현재 실행자로 허용된 읽기만 다시 수행합니다. 이전 actor와 다른 로컬 사용자 ID가 반환되면 표시하지 않습니다. 재조회 시점 이후에도 원래 변경이 완료될 수 있으므로 필요하면 **최신 상태 조회**를 다시 누릅니다. 인증/조회 권한 때문에 재조회할 수 없다면 불가 상태를 표시합니다. 새 변경 요청은 새 미리보기와 실행 클릭이 필요합니다.

변경 전송 중 중복 실행·폼 제출은 차단됩니다. 토큰 변경·연결 해제·401·재연결·페이지 종료는 이전 사용자 대화, 미리보기의 실행자·대상, 입력값과 진행 요청을 초기화합니다. 이전 계정의 늦은 변경 결과나 자동 재조회는 새 계정의 화면에 적용하지 않습니다. 목록 선택을 위해 현재 허용 카탈로그를 연결 세대 안의 메모리에 잠시 보유하며, 계정 변경·연결 해제·401·재연결·변경 실행·최신 상태 재조회 시 선택지와 관계 표시를 초기화합니다. 이름→ID 캐시는 만들지 않습니다. 선택지와 미리보기는 이전 연결에서 재사용되지 않으며 새로운 서버 조회 없이 부여 권한을 만들어 내지 않습니다.

## 오류와 안전성

| 안내 | 의미 |
| --- | --- |
| 인증할 수 없습니다 | HTTP 401. 토큰·화면·미리보기를 지우고 재연결을 안내합니다. 전송한 변경의 결과 미확인 안내는 안전한 일반 문구로 남깁니다. |
| 요청 권한이 부족합니다 | HTTP 403 또는 Tool `FORBIDDEN`. 읽기/관리 scope·DB 관리자 여부·보호된 관계를 서버가 검사합니다. |
| 대상을 조회하거나 변경할 수 없습니다 | `NOT_FOUND`. 숨겨진 대상과 없는 대상의 존재 여부를 구분하지 않습니다. |
| 응답 형식/권한 관계 오류 | JSON-RPC ID·타입·참조 관계·변경 응답의 operation/대상/present/impact가 계약과 다릅니다. 원문이나 내부 스택은 표시하지 않습니다. |
| 접속/시간 초과/업스트림 오류 | 고정된 안전 문구로 구분합니다. 전송 후 변경 요청은 결과 미확인으로 처리합니다. |

토큰은 password DOM과 현재 탭 메모리에서만 처리하고 연결 성공 시 password 입력값도 비웁니다. `localStorage`, `sessionStorage`, URL, 앱 로그, 대화에 저장하지 않습니다. 원문 질문에 붙여 넣은 자격 증명을 대화로 복사하지 않도록 정해진 질문 제목과 검증된 ID만 표시합니다. 모든 서버 문자열은 `textContent`로 렌더링합니다.

MCP `2025-06-18`, `initialize` → `notifications/initialized` → `tools/list` → `tools/call`을 사용합니다. 고정 같은 출처 `/mcp`, 리다이렉트 거부, 쿠키 생략, 전체 작업 12초 제한, 응답 128 KiB 제한을 유지합니다. JSON/SSE·분할 UTF-8을 처리하고 종료/잘못된 MIME 시 본문을 취소합니다. 텍스트와 `structuredContent`가 같이 있으면 일치해야 합니다. 12Tool의 strict 입력 스키마와 읽기/변경 어노테이션을 확인합니다. 별도 세션 ID를 저장하지 않습니다.

자기권한 그래프는 중복 ID·누락된 참조·부여 경로를 검증합니다. 카탈로그는 해당 타입의 필수 필드, 보호/요청 가능 boolean, 상세 ID 일치와 목록 중복을 검증합니다. 요청 가능 역할은 공개 메타데이터만 허용합니다. 변경 결과는 미리보기 operation·정확한 관계 인수·boolean 상태와 영향 사용자 ID를 검증하며 필요한 필드만 표시합니다.

## FE 단위 검증과 E2E 구분

Node.js 22, 저장소 루트에서 추가 설치 없이 실행합니다.

```sh
node --check FE/chat.js
node --test FE/tests/chat.test.mjs
```

현재 **64개 단위 테스트**는 기존 자기권한/관계/문장부호·128 KiB·토큰/계정 경합 회귀와 v2의 카탈로그/상세/요청 가능한 역할/12Tool 스키마·어노테이션을 검증합니다. 관리 6종의 명시 클릭·정확 인수·변경 없음·변경 후 읽기, Enter 우회/중복 클릭 차단, 대상 변경 시 미리보기 무효화, 로컬 ID/subject 독립, read 없는 미리보기 거부, 취소/시간 초과/네트워크/파싱/상한/401의 결과 미확인, 재조회 거부와 이전 계정 응답 차단을 포함합니다. 추가된 12개 안내 UI 회귀는 연결 전 5목적군의 연결 안내, 실제 읽기 핸들러 연결, 모든 provenance 경로와 빈 그래프, 4종 목록·상세, 요청 가능 역할과 개념의 구분, 3종 관계 대상 선택·보호 항목·직접 ID 입력, 오류·계정 전환·401 초기화, 변경 후 새 경로 반영을 검증합니다. label·기본 키보드 컨트롤·모바일 CSS·포커스 이동은 소스 및 DOM 대역 수준으로 확인하며 실제 렌더링 검증을 대신하지 않습니다. 닫힌 관계 보기의 summary는 기본 Tab 순서에 포함하며, 실제 Tab/Enter/Space 동작은 TESTER가 직접 포커스 호출 없이 검증합니다.

이 검증은 **DOM/전송 대역 기반 단위 테스트**입니다. 실제 HTTP/MCP/MySQL/브라우저 E2E 통과 증거가 아닙니다. 실제 E2E는 MANAGER의 TEST_READY 이후 TESTER가 합의된 독립 환경에서 수행합니다. FE는 브라우저 세션·서버·Gradle·DB를 기동하지 않습니다. 빌드와 인계 전 실행은 BE, 인계 후 합의 런타임/브라우저는 TESTER가 전담합니다. 토큰 입력 중 스크린샷·트레이스·헤더 덤프를 남기지 않습니다.

## UI 컨트롤과 배포 파일

안내 영역은 `capabilities`, 상태는 `discovery-status`, 목적별 버튼은 `discover-own`, `discover-browse`, `discover-requestable`, `discover-manage`, `discover-concept`입니다. 관계 영역은 `relationship-view`, 제목·요약·역할은 `relationship-title`, `relationship-summary`, `relationship-roles`, 실제 경로 항목은 `relationship-paths > li`입니다. 경로가 없을 때는 안내 항목 하나를 표시합니다.

탐색 컨트롤은 `browse-entity`(users/roles/policies/resources), `catalog-browser`, `browse-item`(실제 ID를 option value로 사용), `browse-id`, `browse-detail`, `browse-status`, `browse-result`입니다. 관리 대상은 `manage-load-targets`, `manage-first-select`, `manage-second-select`로 불러오고 고르며 선택한 ID는 기존 직접 입력란에 반영됩니다. 선택·제약 상태는 `manage-target-status`, `manage-eligibility`입니다.

기존 관리 컨트롤은 `manage-operation`, `manage-first`, `manage-second`, `manage-preview-button`, `manage-preview`, `manage-actor`, `manage-summary`, `manage-execute`, `manage-cancel`, `manage-status`, `refresh-access`입니다. 각 입력에는 접근성 label이 연결되어 있습니다. operation 변경 시 대상 label을 변경합니다.

유일한 배포 원본은 `FE/chat.html`, `FE/chat.js`, `FE/chat.css`이며 BE가 이 세 파일만 같은 출처 정적 자산으로 패키징합니다. `FE/tests/chat.test.mjs`와 이 문서는 배포하지 않습니다.
